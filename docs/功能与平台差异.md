## 本地黑屏根因与三端对齐边界（2026-10-23）

本次确认的直接原因是鸿蒙旧适配把两条不同的媒体链路当成同一条：`LiveListStore.joinLive` 的主 TRTC 已收到实际主播的音视频，但未绑定渲染节点；`AtomicPlayer.startPlay(livekit://...)` 另走播放器链路，在当前无 CDN 返回的房间选择 SDK 生成的 feedback 目标，该目标未收到音视频。原日志中的首帧属于前者，不能证明后者显示成功。SDK `queryLayout` 为空是该播放器路径的现场现象，不能单凭它断言 Kuikly 布局有误。

证据链按不同层级保留：原 ArkUI 节点已挂载且有非零尺寸；将同一 AtomicPlayer 直接绑定真实 Surface 仍黑屏；移除 Kuikly 的 AtomicPlayer 原生 Demo 进房成功但无音视频；使用相同有效身份、实际传输房间和真实发布者的 TRTC 原生 Demo 有首帧 1280×720，且用户确认音画正常。因此当前问题不能归因于 Kuikly 遮挡或鸿蒙设备不能解码。**SDK 为什么选择该 feedback 路径，以及该房间需要何种服务端配置，尚需腾讯确认；不能据此宣称所有 AtomicPlayer 房间都失效。**

本地观看候选复用 `joinLive` 已使用的主 TRTC：在进房前添加本会话 callback，等待 SDK owner 的真实视频可用事件及 `liteavsdk` XComponent ready 后调用公开 `startRemoteView`。只移除自身 callback、停止自身视频，仍由原 `leaveLive` 退房，不另行 `enterRoom/exitRoom/destroy`。公开接口语义见[腾讯 HarmonyOS TRTCCloud](https://cloud.tencent.com/document/product/647/129076)。该做法在锁定的 SDK 组合上完成静态共享实例核对及真实 HAR、宿主 Kotlin/ArkTS 编译，原生行为测试 21/21 通过。和合康本地签包 SHA-256 `0dd7a406db27ff1897f678fb16d3f8623e9ae9742769b11f1c948a141836f76f` 已覆盖安装，用户确认观看音画正常；退出重入与前后台恢复也已由用户确认正常；列表预览未验收。腾讯升级后需复验共享实例、回调共存和退房行为。

- `sendBarrage`/`like`/`toggleFollow`/`refreshAudience`、快照与join/kicked/end/禁言等事件按会话代次归属。messages含sequence/timestamp/sender/content/businessId/data/kind；sequence不能单独当全局唯一ID。业务点赞上报、文案本地化和消息UI由宿主消费。
- `AndroidLiveSdkRuntime`/`IosLiveSdkRuntime`门禁不自行生成UserSig或代替真实登录。iOS需安装宿主bridge；关闭账号资格并停止预览后再清账号，共用IM身份的借用/自有规则须与客服串行协调。
- Android `AtomicXSession.isLoggedInAs` 与 iOS `GycLiveClient.isLoggedInAs` 按实际 V2TIM 用户和 AtomicX/IM 登录状态判定；异步 `loginUserInfo` 为空、迟到或旧值不参与认证。登录 completion 仍检查 SDKAppId 与操作代次，成功后独立同步 nickname/avatar；资料写入完成不属于登录成功承诺。owned logout 真正调用 SDK，borrowed/foreign/AppId 接管只清本组件状态。
- 点赞共同能力不等于相同UI入口：`like()`发起命令，已注入native reporter在SDK确认成功后报告批次数；snapshot的likeEffectSequence只服务效果触发，不能当业务上传ACK。`LiveLikeBatcher`是core内部实现，不是UI公开参数。[Android原生注入](../live-kuikly/src/androidMain/kotlin/io/github/gycrosskit/livesdk/GycLiveView.kt)、[Swift原生注入](../live-kuikly/ios/GycLiveView.swift)、[iOS Controller](../live-kuikly/src/iosMain/kotlin/io/github/gycrosskit/livesdk/IosKuiklyLiveController.kt)。
- Main同步 `stopActivePreview` 与Renderer可挂起 `stopActivePreviewAndAwait` 不可互换。不要阻塞Renderer/Main互等。
- PiP `accepted`只表示平台请求受理/实验接口提交，不表示浮窗可见；真实状态须宿主回报。iOS实验接口、AndroidActivity PiP、应用内小窗是不同接线，不能用共同snapshot当视觉证据。

iOS 互动只允许持有原生 view 且已 joined 的 session 发起。排队、结束及释放后的实例不能写当前全局 Store；点赞实际批次同样检查归属。释放时仅已 joined 的旧 owner 可在让出令牌前冲刷尾批，迟到的弹幕成功回执按失败结算。

## 差异分类与使用边界

| 分类 | 当前合同与限制 |
| --- | --- |
| 组件接口 | core typed callbacks 与 Kuikly raw/controller/event 分层；Composable 补齐声明更新与释放接线，不复制会话状态机。Kuikly raw/Composable 没有 likeReporter prop，Android在注册工厂创建GycLiveView后设置likeReporter，iOS在Swift GycLiveView创建后设置likeReporter并交给IosKuiklyLiveController，必须在创建观看会话前完成。两端默认None。 |
| OS/SDK边界 | Android AtomicX与iOS AtomicXCore/RoomEngine是不同版本SDK；PiP系统接口/实验接口语义不同，accepted不等于可见。 |
| 宿主输入 | 账号、SDKAppId、UserSig、房间、nickname/avatar、业务点赞、页面生命周期与真实PiP回报必须由宿主下发。相同房间active变更不能只写在viewInit。 |
| 排除 | 鸿蒙首批不含连麦、PK、开播、关注/粉丝、独立IM业务群监听和业务点赞reporter；已发布 HAR 的 PiP 返回 false。本地系统 PiP 候选只由真实系统回调更新状态，不能把请求受理或宿主预布局提示当成进入成功。 |
| 未验收 | 通用原生宿主、列表预览、后台硬件资源完整释放、弱网重连、竖向 PiP 及 vendor 权限未验收；和合康 Kuikly 当前源码包的音画、前后台和 PiP 分项证据见页首，不扩展为所有宿主通过。 |
